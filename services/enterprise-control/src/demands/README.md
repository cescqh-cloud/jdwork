# 需求中心与钉钉 OA

登录企业控制台后打开「需求与审批」。原生客户端走同一套 `/api/v1/demands` 接口。`/openapi.json` 提供请求和响应结构。

## 服务端配置

| 配置 | 用途 |
| --- | --- |
| `ENTERPRISE_DINGTALK_TENANT` | 已登记且启用的组织代码 |
| `ENTERPRISE_DINGTALK_CORP_ID` | 与企业内部应用一致的钉钉企业标识 |
| `ENTERPRISE_DINGTALK_APP_KEY`、`ENTERPRISE_DINGTALK_APP_SECRET` | 企业内部应用凭据。由服务端环境注入 |
| `ENTERPRISE_DINGTALK_CALLBACK_TOKEN`、`ENTERPRISE_DINGTALK_CALLBACK_AES_KEY` | HTTP 事件的签名和解密参数 |
| `ENTERPRISE_DINGTALK_CALLBACK_RECEIVER` | 解密后校验的接收方标识。默认使用应用 Client ID |
| `ENTERPRISE_DEMAND_PRECHECK_MODEL` | 模型中心登记的企业预审模型，需允许处理内部数据和发起人访问 |

管理员在「钉钉审批设置」维护已授权模板的表单映射和员工身份映射。服务端按发起人对应的钉钉用户和部门提交。发起方向需填写需求名称、涉及系统、类型、现状与问题和一个专用的「工作台版本标识」文本字段。版本标识和关键业务字段需能通过实例详情原样读取。没有专用映射的收益、验收要求、责任人、紧急程度和附件引用会随现状正文送审。附件引用支持名称和标识，原文件的上传和下载需要另行接入钉盘权限。

需要发起人自选审批人时，为模板设置节点 `actionerKey` 和允许选择的用户。工作台将选项传到原模板的自选节点，审批流程及其固定节点仍由钉钉配置。 [钉钉发起审批实例](https://dingtalk.apifox.cn/api-141001751)

启用 HTTP 事件时，将 `https://企业控制台域名/api/v1/integrations/dingtalk/组织代码/callback` 填入企业应用的事件订阅，选择审批实例开始、结束、终止。控制台只接收签名、时效、接收方和企业标识相符的加密事件。上线前应在指定的非生产模板核对应用可访问范围和读写权限。 [配置 HTTP 推送](https://dingtalk.apifox.cn/doc-3646230) · [审批实例事件](https://dingtalk.apifox.cn/doc-3659374)

## 工作流和失败恢复

- 绑定设备后，桌面的「保存到本机」将草稿加密保存在当前设备作用域。退出并重新启动可从「本机草稿」继续编辑。离线、登录凭据过期或云端版本策略拦截时，仍可保存和导出 Markdown。解绑前可先导出需要带走的本机草稿。
- 桌面的「保存到云端」只同步草稿。每次保存都带一个持久的请求键，响应丢失后重试会返回原保存回执。草稿在云端发生变化时，修订号校验会拒绝覆盖，并保留本机副本供比对。发起钉钉审批需要另行点击送审。
- 草稿可以先保存。预审结果只对应提交给模型的草稿修订，服务端遮罩明显的凭据并省略责任人和附件引用。含可识别凭据的草稿须清理后才能发往钉钉。
- 点击送审后，数据库先冻结表单和 SHA256，再安排后台建单。同一请求键重复提交会返回同一版本。成功建单只进入审批中。
- 钉钉通知进入去重队列。后台读取实例详情，取得完成且同意、完成且驳回，或终止状态后才记录结论。核对同意时同时校验送审表单。审批期间编辑草稿可以继续，先前审批只保留原版本。 [查询审批实例详情](https://dingtalk.apifox.cn/api-141004134)
- 发起结果不明时，系统按授权模板、发起人和已保存的版本证据补查。只有唯一可核对的实例才会绑定。无法核对时保留待核查状态，避免重复建单。明确的参数拒绝或发起前凭据失败可以在修正后重新提交。 [查询审批实例 ID](https://dingtalk.apifox.cn/api-141006691)
- 已关联的未决审批会定期核对。可用「补查审批状态」提前排队。管理员也可对已授权导入的模板分段补查最近 24 小时内的实例。未匹配的钉钉发起人或表单字段会进入导入待确认，由信息中心负责人复核。
- 已确认同意的版本进入需求池等待人工排期。ERP 修改、SQL 执行和生产发布由各自的授权流程处理。

`POST /api/v1/demands` 和 `PATCH /api/v1/demands/{id}` 支持可选的 `idempotencyKey`。携带时，响应的 `draftMutation` 返回此次保存实际写入的修订。重复请求可能同时返回更晚更新的需求详情，后续编辑仍使用回执里的草稿修订号进行比对。部署支持草稿同步的桌面版本前，先在企业控制服务应用 `0011-demand-draft-requests.sql`。

## 隔离验证

在控制服务目录设置 `ENTERPRISE_TEST_DATABASE_URL`，使用 `test/README.md` 所述的本机临时数据库。运行 `bun --no-env-file test test/demands.dingtalk.test.ts test/demands.integration.test.ts`。测试覆盖真实 PostgreSQL 迁移、权限、并发提交、冻结、补查和回调去重。钉钉接口和模型均使用模拟实现。
